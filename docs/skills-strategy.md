# Skills Strategy

This document defines how reusable skills should be used in the agentic delivery system.

## Purpose

Skills capture repeatable procedures that agents should use across projects.

Use a skill when a workflow needs more structure than a prompt, but does not need to become application code.

## What belongs in a skill

Create skills for repeatable workflows such as:

- contract intake
- requirements extraction
- architecture review
- task decomposition
- pull request review
- accessibility review
- security review
- release checklist execution
- retrospective and lessons capture

A skill may include:

- instructions
- checklists
- templates
- examples
- scripts
- reference documents

## What does not belong in a skill

Do not use skills for:

- one-off project decisions
- client-specific secrets
- production credentials
- private client data
- broad preferences that belong in `AGENTS.md`
- repository settings that belong in `.codex/config.toml`
- executable product code that belongs in a client application

## Relationship to agents

Agents define roles.

Skills define repeatable methods.

For example:

- `requirements_analyst` is an agent.
- `requirements-intake` could be a skill.
- `code_reviewer` is an agent.
- `pull-request-review` could be a skill.

An agent may use multiple skills when the task calls for them.

## Skill boundaries

Skills must preserve the system's safety rules:

- no secrets in source control
- no production changes without approval
- no direct pushes to protected branches
- no unbounded agent work
- no claims that code was generated by an agent
- no billing or account changes without approval

## Initial skill candidates

Create these first:

- `contract-intake`
- `requirements-extraction`
- `architecture-decision`
- `task-decomposition`
- `pull-request-review`
- `qa-evidence`
- `security-review`
- `retrospective`

Do not create all skills at once. Add them when the workflow is clear enough to encode.

## Implemented workflow skills

- `contract-intake`
- `architecture-recommendation`
- `project-setup`
- `task-decomposition`

`task-decomposition` is the required boundary between an approved project scaffold and
implementation. It produces draft task files and a human review gate; it does not
approve or execute tasks. It may produce a human-authorized partial plan when all
omitted requirements and acceptance criteria have explicit reasons and re-entry
conditions; unresolved work is never silently dropped.
